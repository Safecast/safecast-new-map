## How the Radiaverse / RadiaMaps H3 Grid Layer Works

Based on what I could gather (the site blocks automated fetching, so this is reconstructed from the FAQ, ToS, UI elements, and the RadiaMaps interface), here's the architecture:

### 1. H3 Resolution & Zoom Mapping

The RadiaMaps UI exposes a `HEX_RESOLUTION` control with an "Auto (Adjusts with Zoom)" mode and manual overrides from resolution 3 (world scale) through 15, with named levels: 3=WORLD, 4=CONTINENTAL, 5=COUNTRY, 6=REGION, 7=CITY, 8=DISTRICT, 9=BLOCK, 10=BUILDING, then 11–15 unnamed. So the hexagon grid dynamically adjusts resolution as you zoom in/out — this is the standard multi-resolution H3 approach where the map viewport zoom level is mapped to an appropriate H3 resolution.

### 2. Data Pipeline (Server-Side)

The backend does the heavy lifting:

- **Ingestion**: Users upload track files from RadiaCode devices. The system calculates derived data including speed and H3 indices from the raw GPS + dose rate readings.
- **Speed filtering**: Readings taken at over 100 mph are filtered out of the hexagon averaging algorithm — this removes noisy highway/aircraft data that would skew the averages.
- **H3 indexing**: Each valid reading's lat/lng is converted to an H3 cell index at the relevant resolution(s) using `latLngToCell()`. The backend likely pre-computes indices at multiple resolutions, or computes parent cells on the fly from a fine-resolution index.
- **Aggregation**: All valid uploaded data is always used anonymously to calculate the aggregated average dose information displayed in the map's hexagons. So each hexagon shows the mean dose rate (in µSv/h) of all readings that fall within that cell.

### 3. Frontend Rendering

The map is most likely built with **Mapbox GL JS** (the UI shows Mapbox-style map style options like Satellite, Outdoors, Streets, Navigation Day/Night) combined with either:

- **deck.gl's `H3HexagonLayer`** — the most common approach for rendering H3 cells on Mapbox. It takes an array of `{h3index, value}` objects and renders filled/stroked hexagons with color mapping. This is very efficient for large datasets since it can use instanced rendering.
- Or a custom GeoJSON layer where hexagon boundaries are computed from H3 indices using `cellToBoundary()` from h3-js.

Given the cyberpunk styling and the performance needed for potentially hundreds of thousands of hexagons globally, deck.gl's H3HexagonLayer is the most probable choice.

### 4. Color Mapping

The hexagons are color-coded by aggregated dose rate, likely using a gradient from green/blue (low background, ~0.05 µSv/h) through yellow/orange to red (elevated levels). The UI also supports toggling hexagons on/off and switching dose rate units between nSv/h, µSv/h, and mSv/h.

### 5. Two-Layer System

The UI has separate toggles for "Show Readings" and "Show Hexagons", indicating two distinct layers: raw individual data points (scatter/dot layer) and the aggregated H3 hexagon overlay. The readings layer also has a `READINGS_LIMIT` control (All, None, 20k–200k) for performance management.

### Key Technical Differences from Safecast's Approach

This is interesting to compare with Safecast's tilemap approach. RadiaMaps/Radiaverse uses H3 for spatial binning rather than Safecast's traditional raster tile approach. The advantages are the multi-resolution hierarchy (zoom in → finer hexagons automatically), equidistant neighbors for cleaner spatial analysis, and the ability to do server-side pre-aggregation by H3 index which maps efficiently to database queries (e.g., `GROUP BY h3_index`).
